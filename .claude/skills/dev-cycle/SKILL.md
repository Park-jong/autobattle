# dev-cycle

사용자가 지시한 코드 작업을 **개발 → 검증 → 피드백** 에이전트 사이클로 처리한다.
메인 에이전트(나)는 조율만 한다. 코드 작성·검증·피드백은 각 에이전트에게 맡기고, 직접 코드를 고치지 않는다.

| 역할 | 에이전트 (`subagent_type`) | 하는 일 |
|------|---------------------------|---------|
| 개발 | `code-writer` | 구현, 피드백 반영 수정 |
| 검증 | `code-verifier` | 테스트·빌드·린트 실행, 요구사항 대비 확인 (코드 수정 안 함) |
| 피드백 | `feedback-synthesizer` | 검증 결과를 근본 원인과 수정 지시로 정리 |

## 0. 준비

1. 지시 내용을 **완료 조건** 목록으로 정리한다 (무엇이 되면 끝인지, 범위 밖은 무엇인지). 지시가 애매해 결과가 크게 달라질 수 있으면 시작 전에 사용자에게 묻는다.
2. 프로젝트 지침(CLAUDE.md, TODO.md 등)과 관련 파일을 확인해, 에이전트에게 넘길 맥락(대상 파일, 컨벤션, 테스트·빌드 명령)을 모은다.
3. 사용자에게 완료 조건을 한 줄씩 짧게 알리고 바로 시작한다 (승인을 기다리지 않는다).

## 1. 사이클 (최대 3회)

각 사이클은 **개발 → 검증 → (실패 시) 피드백** 순서다. 에이전트는 이전 대화를 모르므로, 매번 프롬프트에 필요한 맥락을 모두 적는다.

### 개발 — `code-writer`
- 사이클 1: 원래 지시, 완료 조건, 대상 파일, 프로젝트 컨벤션을 넘긴다.
- 사이클 2~3: 위 내용에 더해 **직전 feedback-synthesizer의 수정 지시**를 그대로 넘기고, 지시 범위 밖은 고치지 말라고 적는다.
- 결과로 변경한 파일과 변경 요약을 받는다.

### 검증 — `code-verifier`
- 원래 지시, 완료 조건, 변경된 파일 목록, 실행할 테스트·빌드 명령을 넘긴다.
- code-writer의 자체 평가("잘 동작함" 등)는 넘기지 않는다. 독립적으로 판단하게 한다.
- 사이클 2~3에서는 직전 사이클에서 발견된 문제 목록도 넘겨, 해결됐는지와 **회귀**가 없는지 함께 확인하게 한다.
- 결과를 반드시 `통과` / `실패` 판정과 문제 목록(심각도: 높음/중간/낮음, 위치, 재현 방법)으로 받는다.

### 판정
- **통과**: 완료 조건을 모두 만족하고 높음·중간 문제가 없으면 사이클을 끝내고 '2. 완료 보고'로 간다. 낮음 문제는 고치지 않고 보고에 남긴다.
- **실패**: 피드백 단계로 간다.

### 피드백 — `feedback-synthesizer`
- 검증 결과 전문, 원래 지시, 완료 조건, 지금까지의 사이클 이력(각 사이클에서 무엇을 고쳤고 무엇이 남았는지)을 넘긴다.
- 결과로 근본 원인과 code-writer가 바로 실행할 수 있는 수정 지시 목록을 받는다.
- 같은 문제가 두 사이클 연속으로 남아 있으면, 이전 접근이 왜 실패했는지와 다른 접근을 제안하게 한다.
- 수정 지시를 받으면 다음 사이클의 개발로 넘어간다.

### 진행 알림
각 단계가 끝날 때마다 사용자에게 한 줄로 알린다 (예: `사이클 1 검증: 실패 — 높음 1, 중간 2`).

## 2. 완료 보고 (통과한 경우)

- 몇 번째 사이클에서 통과했는지
- 변경한 파일과 변경 요약
- 검증에서 실제로 실행한 테스트·빌드와 결과 (실행하지 못한 검증이 있으면 그렇다고 적는다)
- 남은 낮음 문제와 확인하지 못한 부분

## 3. 실패 보고 (3번째 사이클 검증도 실패한 경우)

4번째 사이클은 시작하지 않는다. 멈추고 아래를 보고한 뒤 사용자 결정을 기다린다.

- 해결되지 않은 문제 목록 (심각도, 위치, 재현 방법)
- 사이클별 이력: 각 사이클에서 시도한 수정과 그 결과
- 해결되지 않는 이유에 대한 판단 (예: 요구사항끼리 충돌, 설계 변경 필요, 환경 문제로 검증 불가)
- 다음 선택지 2~3개와 추천 (예: 요구사항 조정, 다른 접근으로 사이클 재시작, 부분 완료로 마무리)
- 현재 코드 상태: 수정이 적용된 채로 남아 있다는 사실과 변경된 파일 목록

## 규칙

- 사용자가 지시한 범위만 진행한다. 검증 중 범위 밖 문제를 발견하면 고치지 말고 보고에만 남긴다.
- 사이클 횟수는 검증 실패 → 수정이 일어날 때마다 센다. 사용자가 중간에 지시를 바꾸면 사이클을 1부터 다시 센다.
- 검증 환경 문제(테스트 실행 불가, 의존성 없음 등)로 판정할 수 없으면 사이클을 소모하지 말고 바로 사용자에게 알린다.
- 커밋·push는 하지 않는다. 사용자가 커밋을 요청하면 그때 `commit-release` 스킬을 쓴다.
