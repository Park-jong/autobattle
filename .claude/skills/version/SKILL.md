# version

마지막 버전 이후의 변경 내용을 읽고 **올릴 버전을 판단해 파일에 반영**한다.
`git add`, `git commit`, `git tag`, `git push`는 실행하지 않는다. 커밋과 태그는 사용자가 직접 한다.

인자로 `major` / `minor` / `patch`를 받으면 판단을 건너뛰고 그 단계로 올린다. `1.0.0`처럼 버전을 직접 주면 그 값으로 설정한다 (현재보다 낮으면 경고하고 멈춘다).

## 절차

1. **현재 버전 찾기** — 아래 순서로 처음 발견한 곳을 버전의 기준(source of truth)으로 쓴다.
   1. `package.json`의 `version`
   2. `pyproject.toml`(`[project]` 또는 `[tool.poetry]`)의 `version`, `Cargo.toml`의 `[package] version` 등 언어별 매니페스트
   3. 프로젝트 루트의 `VERSION` 파일 (한 줄, `0.0.0` 형식)

   어디에도 없으면 루트에 `VERSION` 파일을 `0.0.0`으로 만들고, 현재 버전을 `0.0.0`으로 본다.
   버전 문자열이 `MAJOR.MINOR.PATCH` 형식이 아니면 고치지 말고 사용자에게 알린 뒤 멈춘다.

2. **비교 기준점 정하기** — "마지막 버전 이후"의 시작점을 정한다.
   - git 저장소면: `git tag --list "v*"`에서 현재 버전과 같은 태그(`v<현재 버전>`)가 있으면 그 태그, 없으면 `git log -n 1 --format=%H -- <버전 파일>`로 버전 파일을 마지막으로 바꾼 커밋. 둘 다 없으면 저장소 전체가 대상이다.
   - git 저장소가 아니면: `CHANGELOG.md`의 마지막 항목 날짜 이후 수정된 파일을 대상으로 보고, 파일 내용을 직접 읽어 판단한다. CHANGELOG도 없으면(첫 실행) 프로젝트 전체를 첫 버전의 내용으로 본다.

3. **변경 내용 분석** — `git log <기준>..HEAD`, `git diff <기준>`(작업 트리의 미커밋 변경 포함), `git status`(untracked 파일은 내용을 직접 읽는다)로 무엇이 바뀌었는지 파악한다. 커밋 메시지의 type(`feat`, `fix` 등)은 참고만 하고, 실제 코드 변경으로 판단한다.

4. **올릴 단계 판단** — 아래 '판단 기준'으로 변경 하나하나를 분류하고, 가장 높은 단계 하나를 고른다.

5. **반영**
   - 버전 파일의 값을 새 버전으로 바꾼다. 같은 버전이 다른 곳에도 적혀 있으면(예: `package-lock.json`의 루트 `version`, 코드 안의 `VERSION` 상수) 함께 맞춘다. 그 밖의 파일은 건드리지 않는다.
   - 루트 `CHANGELOG.md`의 맨 위(제목 바로 아래)에 새 항목을 추가한다. 파일이 없으면 만든다.

6. **보고** — 이전 버전 → 새 버전, 고른 단계와 그 근거가 된 변경, 수정한 파일 목록을 짧게 알려준다. 사용자가 직접 실행할 태그 명령(`git tag v<새 버전>`)은 안내만 한다.

## 판단 기준

| 단계 | 언제 | 예 |
|------|------|-----|
| **MAJOR** | 기존 사용자(호출하는 코드, 저장 데이터, 설정)가 수정 없이는 더 이상 동작하지 않는 변경 | 공개 함수·API의 삭제/이름 변경/시그니처 변경, 저장 파일 형식이 바뀌어 이전 데이터를 못 읽음, 필수 설정 추가, 기존 동작의 의도적 변경 |
| **MINOR** | 하위 호환을 유지하면서 기능이 추가된 변경 | 새 기능·화면·옵션·API 추가, 선택적 설정 추가, 기존 기능의 눈에 띄는 확장 |
| **PATCH** | 동작을 바꾸지 않거나 잘못된 동작을 바로잡는 변경 | 버그 수정, 성능 개선, 내부 리팩터링, 밸런스·수치 조정, 의존성 패치 업데이트 |
| 올리지 않음 | 배포물에 영향이 없는 변경만 있을 때 | 문서·주석, 테스트만 추가, 개발 도구·CI 설정, 포맷팅 |

- **0.x 단계 규칙** (현재 MAJOR가 0일 때): 아직 공개 API가 안정되지 않은 단계로 본다. 호환이 깨지는 변경은 MAJOR 대신 **MINOR**를 올리고, 기능 추가도 **MINOR**, 그 밖은 **PATCH**다. `1.0.0`으로는 스스로 올리지 않고, 사용자가 `major` 또는 `1.0.0`을 명시했을 때만 올린다.
- 단계를 올리면 아래 자리는 0으로 초기화한다 (예: `0.3.4` → MINOR → `0.4.0`, `1.2.3` → MAJOR → `2.0.0`).
- 비교 대상 변경이 없거나 '올리지 않음'만 있으면 파일을 바꾸지 않고 그 이유를 알려준다.
- 호환성이 깨지는지 애매하면 낮은 쪽으로 단정하지 말고, 두 후보와 각각의 근거를 보여준 뒤 사용자에게 고르게 한다.

## CHANGELOG 형식

```
# Changelog

## [<새 버전>] - <YYYY-MM-DD>
### Breaking
- <호환이 깨지는 변경과 사용자가 해야 할 조치>
### Added
- <추가된 기능>
### Fixed
- <수정된 버그>
### Changed
- <그 밖의 동작·수치 변경, 리팩터링, 성능>
```

- 내용이 없는 소제목은 넣지 않는다.
- 불릿은 한글로, 파일 이름이 아니라 사용자 입장에서 무엇이 달라졌는지를 쓴다.
- 날짜는 오늘 날짜를 쓴다.

## 금지

- `git add`, `git commit`, `git tag`, `git push`, `git reset` 등 저장소 상태를 바꾸는 명령 실행 금지.
- 버전을 낮추거나, 판단 근거 없이 단계를 올리는 것 금지.
- 버전 파일과 CHANGELOG 외의 파일 수정 금지 (같은 버전 값을 담은 파일 동기화는 예외).
